# Как применялся TDD

Цикл для каждой возможности:

1. **Red** — пишем тест на ещё не существующее поведение, запускаем
   `pytest`, убеждаемся, что тест падает по правильной причине.
2. **Green** — пишем минимальный код, чтобы тест прошёл.
3. **Refactor** — улучшаем код, не меняя поведения; тесты остаются
   зелёными.

## Калькулятор (модель)

| Шаг | Тест | Реализация |
|-----|------|------------|
| 1 | сложение, вычитание, умножение, деление | `BINARY` со словарём операций |
| 2 | деление на ноль → `CalculatorError` | `_divide` |
| 3 | `sqrt`, `negate`; ошибка для отрицательного корня | `UNARY`, `_sqrt` |
| 4 | неверное число аргументов, неизвестная операция | проверки в `calculate` |
| 5 | история, её копия, лимит, очистка | `_history`, `_remember` |
| 6 | степень: комплексный результат и переполнение | `_power` |

## API

| Шаг | Тест | Реализация |
|-----|------|------------|
| 1 | `GET /health` → 200 | `create_app`, маршрут `health` |
| 2 | `POST /calculate` возвращает результат и выражение | view `CalculationResponse` |
| 3 | ошибка модели → 400, неверное тело → 422 | перехват `CalculatorError`, `Literal` в схеме |
| 4 | `GET/DELETE /history` | маршруты истории |
| 5 | два приложения не делят состояние | модель в `app.state` |

В истории git каждому шагу соответствуют коммиты `test:` → `feat:`
(и при необходимости `refactor:`).
